# EventRadar — этап 1 (0.1.0)

Нативный Android-клиент на Flutter и первая серверная миграция Supabase.
Это начало разработки по ORIGINAL_SPEC.txt, **не готовая платформа продажи билетов**.

## Что находится в проекте

- Material 3, Riverpod, GoRouter, Freezed/json_serializable.
- Каталог из Supabase: полнотекстовый поиск, город, категория, страницы по 30 записей.
- Карточка события: описание, оригинальный язык, адрес и время в зоне мероприятия.
- Регистрация/вход по email, выход; токены через Flutter Secure Storage.
- Избранное гостя локально, авторизованного пользователя — на сервере; добровольный перенос.
- Русский, узбекский, английский; выбор языка Android с русским fallback.
- Системная/светлая/тёмная темы; настройки сохраняются.
- PostgreSQL: справочники, профили, роли, заявки организаторов, события/даты/переводы,
  избранное, приватные ссылки доступа, audit log.
- RPC подачи/рассмотрения заявки, создания черновика, публикации; RLS и серверные проверки.
- Три SVG-концепции бренда, выбранный radar, светлый/тёмный логотип, Android-иконка.

В UI пока две вкладки: каталог и профиль. Карта, билеты, кабинет и админ-панель
добавляются по этапам; неработающие вкладки не включены в эту сборку.
В базе нет фиктивных событий, платежей или билетов. Справочники содержат Узбекистан,
Фергану, Ташкент и 16 категорий. Другие страны добавляются позже.

## Подключение на компьютере разработчика

1. Установить Flutter stable и Android SDK; выполнить `flutter doctor`.
2. Создать **тестовый** Supabase-проект. SQL миграции применяются последовательно:
   `supabase/migrations/202611070001_foundation.sql`, затем `202611070002_reference_data.sql`.
   Можно использовать SQL Editor или Supabase CLI (`supabase link`, `supabase db push`).
3. В Auth включить email registration и подтверждение email, настроить SMTP.
   Минимальная длина пароля — 12 символов; production требует CAPTCHA и rate limits.
4. В Data API оставить exposed schemas `public` (и системный `graphql_public`, если нужен).
   Не добавлять `private`. RLS из миграции не отключать.
5. Скопировать `config.example.json` в `config.json`, указать URL проекта и **publishable**
   ключ. Это публичные параметры, допустимые в APK. Никогда не вставлять service_role,
   `sb_secret_…`, ключи мерчанта, пароли или ключ подписи.
6. Установить зависимости и создать генерируемые файлы:

```sh
flutter pub get
flutter gen-l10n
dart run build_runner build
flutter run --dart-define-from-file=config.json
```

Без `config.json` можно запустить `flutter run`: будет экран подключения, профиль и настройки.
На первом этапе email подтверждается по письму; после этого пользователь возвращается в
приложение и входит вручную. Password reset, Google Sign-In, OTP и App Links пока не реализованы.

## Серверный сценарий организатора

UI кабинета ещё не создан. RPC можно проверять из доверенного тестового клиента
с JWT конкретного пользователя; SQL Editor по умолчанию не имеет `auth.uid()`.

1. Подтверждённый пользователь вызывает `submit_organizer_application`.
2. Владелец БД назначает первоначального admin только конкретному проверенному UUID
   через `user_roles`. Это ручной bootstrap, не функция мобильного приложения.
3. Admin вызывает `review_organizer_application(id,true)`.
4. Организатор вызывает `create_event_draft`, затем `publish_event`.
5. Опубликованное событие появляется в гостевом каталоге.

Подробные RPC-аргументы — в миграции, проверки сценария — в `tests/db/foundation.test.mjs`.
Не использовать SQL Editor с postgres-правами для проверки RLS: он обходит политики.

## Проверки

```sh
flutter analyze
flutter test
npm ci
npm run test:db
```

`tool/check.sh` объединяет генерацию и проверки (требует Flutter и Node.js).
Тесты БД используют отдельный PostgreSQL WASM (PGlite) с тестовым контрактом `auth.uid()`.
Они реально выполняют миграции и RLS, но не заменяют тесты Supabase Auth/Data API,
параллельных соединений, Android-эмулятора или платёжных интеграций.
Тестовые пользователи находятся только в тестах.

## Android

Имя пакета: `uz.eventradar.app` (зарегистрировано для Google Play, не менять).
Минимальная версия: API 24; compile/target берутся из установленного Flutter SDK.
Для debug: `flutter build apk --debug --dart-define-from-file=config.json`.
Конфигурация release не подписывает сборку debug-ключом. Подключить отдельный keystore,
внешние секреты подписи и проверить требования Google Play перед релизом.
AAB для публикации сейчас не готовится: продукт ещё не прошёл критерии приёмки.

## Интеграции этапа 2 (Карта, Push-уведомления, Платежи)

### 1. Карта и картографический провайдер
- Интерактивная карта мероприятий (`/map`) с фильтрацией по городам и категориям.
- Картографический провайдер **OpenStreetMap (OSM)** настроен по умолчанию и работает из коробки без API-ключей.
- Поддержка переключения провайдеров: CartoDB, Google Maps, Yandex Maps, Mapbox GL с сохранением пользовательских ключей в настройках.
- Метки мероприятий, плавающая карточка события, кнопка построения маршрута во внешнем навигаторе и быстрая покупка билета.

### 2. Push-уведомления (Firebase Cloud Messaging)
- Сервис Push-уведомлений и регистрация токенов устройства (`user_push_tokens`).
- Экран «Push-уведомления» с мониторингом статуса доставки и отображением FCM токена.
- Интерактивный тестовый стенд для мгновенной проверки уведомлений: покупка билета, напоминание за 24ч, напоминание за 1ч, анонс события.
- Всплывающие In-App баннеры и история полученных уведомлений с фильтрацией по категориям.

### 3. Подключение платёжных систем и покупка билетов
- Общий интерфейс `PaymentGateway` и подключённые адаптеры:
  - **Payme** (Uzcard / Humo / Visa) с формированием официальной платёжной ссылки Paycom.
  - **Click** (Click Up / Evolution) с генерацией URL перевода и обработкой статуса.
  - **Банковская карта** (Uzcard, Humo, Visa, Mastercard, Stripe).
  - **Тестовый шлюз** для мгновенной проверки сценариев оплаты в песочнице без списания средств.
- Покупка билетов по тарифам (Входной, Фан-зона, VIP), прозрачный учёт 5% комиссии платформы EventRadar (комиссия удерживается с организатора, 0 сум доплаты для покупателя).
- Электронный билет с уникальным номером, детерминированным QR-кодом для проверки контролёром на входе и экспортом в PDF.
- Экран «Мои билеты» в профиле пользователя.
