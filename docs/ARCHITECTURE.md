# EventRadar — архитектура первого этапа

Android/Flutter → Supabase Auth и Data API → PostgreSQL с RLS.
Каталог и избранное используют Supabase SDK, а не отдельный HTTP-прокси.
Dio оставлен для будущих внешних API, он не дублирует Supabase SDK.

## Реализованные границы

- `core`: конфигурация, защищённая сессия, настройки, тема, зависимости.
- `features/catalog`: Freezed-модель, репозиторий, поиск, фильтры, детали и избранное.
- `features/auth`: email/password регистрация и вход; выход в профиле.
- `features/profile`: настройки и добровольный перенос избранного гостя.
- `supabase/migrations`: источник истины и полномочия; клиент не пишет роли/статусы событий.
- Общий каталог: только опубликованные события, ближайшая ещё не завершённая дата серии.
- Времена: timestamptz + IANA timezone; UI показывает время именно мероприятия.
- Переводы: запрос языка → оригинальный язык; язык описания явно показан.
- Локально: тема, язык, избранное гостя в SharedPreferences; токены — Flutter Secure Storage.
- В production не добавлены демонстрационные события или аккаунты.

## Доступ

Публичны справочники, одобренные организаторы и опубликованные мероприятия.
Профили, заявки и избранное ограничены пользователем; audit log — администратором.
Никаких публичных политик для `event_access`: доступ откроется только после разработки
валидных билетов и серверной проверки регистрации. Текущая сборка не выдаёт доступ.

Подача заявки проверяет email/телефон в `auth.users`, а не пользовательские metadata.
Одобрение и публикация выполняются транзакционно с блокировкой строки и журналом.
Первый администратор назначается владельцем БД вручную, не через клиент.
`private` не включается в список exposed schemas Supabase.

## Следующие этапы

1. Полный интерфейс заявки/модерации/редактора поверх готовых RPC; изменение и загрузка фото.
2. `event_occurrences → ticket_types → inventory → reservations → orders → order_items → tickets`.
3. Серверный резерв на 15 минут с единым порядком блокировок occurrence/inventory;
   повтор запросов по уникальному `(buyer_id,idempotency_key)`.
4. PaymentProvider по договору первого рынка. Проверка webhook, уникальный ID события,
   сверка суммы/валюты, один успешный платёж на заказ, поздняя оплата в отдельном состоянии
   для сверки/возврата; не выдавать билеты из просроченного резерва автоматически.
5. Каждому билету криптографический токен (в БД только хэш). Проверка онлайн атомарно
   переводит valid → used и записывает checker; обновление владельца аннулирует токен.
6. Передача через подтверждение получателя, возвраты первоначальным способом оплаты,
   выплаты по реальному ответу провайдера. Денежные суммы в minor units, комиссия 500 bps
   в снимке продажи. Расчёт и округление отдельно по билету, не по плавающей точке.
7. Realtime чат, доступ по участникам; FCM с outbox и уникальным ключом напоминания.
8. Карта, история поиска, расширенные фильтры, полноценная навигация из пяти вкладок.

Финансовые сущности здесь описаны как проектирование, а не реализованные возможности.

## Решения до платёжного этапа

Первый рынок предполагается Узбекистан (справочники Ферганы и Ташкента), но
нужно подтвердить юридическое лицо, страны продаж и доступные merchant-договоры.
Выбор провайдера не сделан без этих данных. Online-билеты и продвижение требуют
отдельной проверки правил магазина перед интеграцией оплаты.

## Ограничения безопасности первого этапа

Лимиты RPC по количеству записей — базовая защита, не полноценный конкурентно-безопасный
rate limiter. До публикации нужны gateway rate limit, CAPTCHA/OTP-лимиты, MFA для admin,
удаление аккаунта, политика хранения, обработка восстановления пароля, журналы
административного bootstrap/ограничений аккаунта и интеграционные тесты реального Supabase.
Авторизация UI не считается проверенной одним SQL-тестом.
